# Offline core CI

`Offline Core` runs on pushes to `main` and pull requests targeting `main`. It uses Ubuntu 24.04, Python 3.11, SHA-pinned official checkout/setup-python actions and only `contents: read`. A newer run for the same branch or PR cancels the older one.

The job imports public modules, checks CLI parsing and runs selected offline tests in sequential batches, including scripted diagnostic comparison, b11521 observation checks, atomic-write races and explicit static-diagnosis abstention. Every batch uses the existing 120-second deadline, 64 MiB allocated-output monitoring threshold and 2 MiB record limit; the whole job stops after 10 minutes. These are monitored output limits, not filesystem quotas.

Five separate real TCP fixtures then check kernel-assigned loopback listeners, consecutive close/start, live conflicts, a held checking socket and address drift. They run in one Python process, send one byte per simulated service and close every owned socket. Each operation has a one-second timeout and the entire fixture entry has a 30-second guard. This fixed test file is run separately; the offline runner continues to forbid all native socket/HTTP/process dispatch. The fixtures are trusted test code, not an arbitrary-code sandbox or a model-service proof.

No model/VM asset, package installation, dependency cache or artifact upload is used. A failed job prints at most 64 KiB of diagnostic body in its logs. The tests use fresh synthetic fixtures and need only committed core files; they do not validate live services, model quality or arbitrary-code isolation.

Run the explicit test commands from [.github/workflows/offline-core.yml](../.github/workflows/offline-core.yml) locally. Direct full discovery is outside this CI scope. The separate legacy PR-review workflow retains its previous behavior.

The offline runner counts allocation through `macr.memory.atomic_file.tree_usage`. Both real comparison write paths in `diagnostic_compare` use this same strict snapshot for their existing logical-byte record limit. Its snapshot and `atomic_write` share a process-local lock around temporary-file creation and replacement, so a scanner cannot enumerate an atomic temporary file and then lose it to a concurrent replacement. The helper still counts directories, AppleDouble files and temporary files retained after write failure; missing entries and symlinks still fail. The deterministic regression tests force the former enumeration/replacement race through `record_response`, verify the shared module instance, and check missing-file failures through `prepare_comparison`, `record_response` and `save_comparison`. The lock is not held during file writes or `fsync`.

This coordination only covers writers and scanners using the same imported module in one process. `check_mock_recovery.fixture_bytes` keeps its separate semantics for directly owned child fixtures, including their cleanup and link accounting; it does not use this strict helper. Historical frozen model owners, bindings and plans remain unchanged. The local `artifacts/implementation/diagnostic-record-lock-wiring-01` deliverable contains complete derived owner and binding sources with both existing allocation scan bodies wired to `namespace_snapshot`; their callers already reach the updated functions. Their log/weight exclusions, entry checks and budgets are retained. No cross-process coordination or historical whole-run compliance is claimed.

Both derived scans import the context manager lazily through the verified loader, after source admission, and use the canonical `macr.memory.atomic_file` module also used by the recorder. Loading a second copy under another name creates a different lock. Local offline evidence checks the actual derived function bodies with source-pinned loading and controlled races; public CI checks the committed comparison entry points. Neither test is native-service qualification or another model-run grant. A future authorized measurement must freeze its own inputs and source bindings; the consumed historical plan cannot be reused.
