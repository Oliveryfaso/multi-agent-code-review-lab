# 文档维护

功能、接口、安装方式或支持范围发生变化时，在同一批改动中检查相关文档。这份清单补充项目现有规范；执行范围和权限仍按 AGENTS、具体任务授权及测试约束处理。

## 保持读者入口清楚

README 回答项目做什么、适合谁、如何开始和当前限制，链接到详细用法与架构解释。示例来自当前公开代码，默认路径不依赖维护者机器、私有配置或历史运行资产。实验能力和历史记录带明确标记。

详细操作、接口合同、设计理由分别放到现有对应文档；同一个预算或能力边界优先在一处完整维护，其他位置写简短摘要并链接。修改标题或路径时一并检查仓内引用。

## 随改动同步

| 改动 | 同批检查的文档 |
| --- | --- |
| 命令、参数、默认值、安装与包资源 | README 快速开始、命令用法、包声明与相关发布说明 |
| 入口、模块职责、进程、存储或信任边界 | 架构图、模块说明、涉及的安全边界 |
| API/报告字段、状态或错误、取消/恢复行为 | 接口和数据合同、用户用法、兼容性说明 |
| 支持语言/平台、预算、排除规则或新依赖 | README 能力边界、详细限制、安全与安装说明 |
| 新的真实项目验收或已知失败 | 验证范围与结果摘要、剩余限制；保留原失败记录 |
| 内部实现调整且外部行为不变 | 检查原说明是否仍准确；准确时无需凑文档改动 |

架构图以仓内 Mermaid 文本随代码版本维护，展示当前实际调用方向、输入输出和关键边界。用简短文字解释图的范围；计划中的组件明确标记。模块/边界没有变化时无需重画。GitHub 原生支持的图优先，不为简单图新增构建链。

## 区分证据层次

每条结果说明对应版本、环境和测量范围，保留失败与未运行项。源码审查、纯分支/模拟测试、真实 loopback、安装资源、原生资源与进程生命周期、浏览器体验、真实外部项目各自证明对应范围；通过其中一层不能代替其他层。静态源码读取完成不等于根因证明、模型修复成功或整个仓库正确。

文档只引用可公开的摘要和 CI。真实项目源码、原始日志、运行数据库、密钥、模型和个人配置保留在授权的本地范围。缺失的历史观察不能由后来的测试追溯补造。

## 提交与发布前检查

按本次影响做必要检查，不因文档改动自动启动模型、VM、目标代码或大负载测试。

1. 对照当前代码核实新命令、默认值、支持边界和图中模块；检查相对链接、标题锚点及 Markdown 图。命令未实际执行时说明核验层次。
2. 按修改范围运行项目已有的有界检查。文案和图的修改通常只需内容、链接及渲染检查；接口或行为改变再执行对应回归。实际 CI 入口见 [offline-core.yml](../.github/workflows/offline-core.yml)，工作台限制见 [evidence-workbench.md](evidence-workbench.md)。
3. 查看拟提交的精确文件与 diff，排除秘密、个人配置、运行数据/日志、外部 checkout、私有源码和生成大文件，保留用户原有修改。
4. 核对目标 remote 和 branch，正常提交推送；推送后核对精确远端 commit 与该 commit 的 CI，不能引用其他版本的绿灯。
5. 说明用户可见变化、验证证据、失败和未运行范围。发布记录整理有意义的变化、兼容性及已知限制，无需抄录全部提交或测试日志。
