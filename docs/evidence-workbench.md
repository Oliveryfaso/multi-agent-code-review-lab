# Local evidence and repair workbench

The static reading flow captures source through the existing supervisor. It does not execute/import a target, call a model, diagnose a root cause or repair files. Reading completed means the requested reading completed; it is not a whole-repository verdict. The separate [repair-candidate flow](#repair-candidates) uses prepared inputs and the normal repair coordinator under the same workbench owner.

Start it explicitly from the trusted installation, outside the project being read:

```sh
agent-review evidence-ui --data-root /local/owned/macr-evidence
```

Choose an actual owned local directory. The command prints a loopback URL including a short-lived session fragment. Open that complete URL manually. The app removes the fragment from the address bar and keeps its access credential in this tab's sessionStorage. Do not share the bootstrap address. No browser opens automatically; the default startup sends no data off-machine. Explicit remote repair is described below. No third-party runtime dependency or Node build is required.

The default data root is `~/Library/Application Support/MACR Evidence`. It is created only when the command runs. macOS APFS is the primary root environment; a limited set of Linux local POSIX filesystems is recognized for protocol fixtures, which does not establish Linux native worker/pressure support. Windows and shared/network/ExFAT data roots are unsupported. Existing source exclusions and symlink policies still apply. A supported filesystem name alone does not prove a tested configuration.

Fill in an absolute project directory and a nonblank question, then add source entries, qualified symbols or an already-reported traceback. Entries can name a file, `file:qualified_symbol`, `file:line` or `file:start-end`. Question limit is8KiB UTF8, traceback64KiB/64frames, entries+symbols6. The standard profile has a120-second analysis target and5-second cleanup target; the larger profile has240 seconds and larger resource budgets. Targets are not hard guarantees against kernel/device stalls. No profile is raised automatically.

The single page provides input, phase/elapsed time and cancellation, captured source with exact physical lines and completeness, coverage/required gaps, local retained history and original JSON/Markdown downloads. It does not invent file progress or percentages. `coverage.unread` means source not selected for display; those files may have been captured and parsed. Frames and unique source units are counted separately. A valid v2 frame may still reference a partial function body; unsupported parsing or limited syntax is not a diagnosis of a target defect.

An uncommitted analysis failure exposes a bounded code/field/stage summary and, when present, the original effective/observed limit. It remains a failure; source panels and successful exports remain unavailable. The summary is retained for new runs without another target read or dispatch. Older records without it explicitly show that the stage was not recorded. Metadata entry/byte limits count cumulative traversal work, including repeated owned-output monitoring; they are distinct from the number of entries in the retained directory. The unchanged standard/larger profiles share the same20000 metadata-entry and4MiB metadata-byte budgets. The manually selected `standard-capacity` workbench preset uses the existing standard profile with exactly two overrides:100000 cumulative metadata entries and16MiB cumulative metadata bytes. Other standard budgets, exclusions, worker logic,0.1-second allocation checks and0.05-second RSS target stay unchanged. The UI labels the preset before submission; state/history and saved core request/receipt/report retain the full effective profile. Reopening accepts only an exact registered preset, and altered capacity or other fields are rejected. It never selects the preset automatically after a failed run. Its capacity is finite and does not guarantee completion under the time or other guards.

Evidence reading and repair share one active slot, with no automatic retry, restart or queue. An evidence run has one non-daemon supervisor execution thread and at most one analysis worker. Duplicate intent resolution returns the same run. An uncertain submission is queried rather than posted again. An evidence cancel response means cancellation was requested; closure must still be confirmed. A cancellation arriving after valid COMMITTED preserves the completed/partial saved result. Unknown closure blocks new work and is retained across startup; no PID from a saved record is blindly killed.

Use **Exit workbench** or interrupt the foreground command to request evidence cancellation and wait for supervisor cleanup. An active repair coordinator is joined; it has no repair cancellation interface. Closing a browser tab alone does not cancel a run. SIGTERM requests the same graceful path. Forced process death cannot establish worker closure: startup inspects the owned registry/receipts and isolates unresolved runs instead of replaying them.

Only this workbench's registered outputs appear in history. Reopening an evidence report reads the saved snapshot even if the original project moved; it never substitutes current working-tree bytes. A read-only consumer binds the original receipt, documents, manifest and every captured file, and checks displayed excerpt bytes. It does not rebuild AST or re-prove the original semantic observations. Damaged/version-unsupported/budget-stopped readings are distinct and withheld, with original files preserved. Hash associations are not digital signatures or a guarantee against later tampering.

Saved evidence JSON contains worker-render usage. Run details separately show the returned final lifecycle/cumulative usage when retained; these are not the same measurements. The HTTP report response preserves the saved document in `report`; when a final envelope is retained, its `final` object contains only `run` and `usage`. Exports are original verified JSON/Markdown bytes, with local paths, input and selected source; handle them as local sensitive material. Export errors do not rerun analysis or revoke a committed result.

The data root is held by a fixed-file-descriptor cross-process lock until shutdown. A second owner is refused. Evidence and repair share the2GiB retained physical-allocation cap and5MiB owned-metadata cap. An evidence run reserves its profile allocation maximum plus8MiB metadata/allocation margin; repair uses a separate conservative reservation under the same root cap. No existing output is overwritten and nothing is automatically deleted. Capacity refusal requires inspection/manual handling of the specific owned old outputs. Whole-root checks are bounded by10 seconds,100000 entries and16MiB estimated metadata. Evidence report verification is serial, up to256MiB IO and a10-second target, using the original metadata limits; during analysis only an already-loaded old evidence report can be read in the browser. Repair does not inherit the evidence supervisor's worker RSS/deadline monitors or the evidence reader's cumulative IO/time budget.

The HTTP adapter binds only127.0.0.1 on an ephemeral port, caps connections at4 before starting request threads, socket operations at10 seconds, headers at16KiB and bodies at128KiB. All API reads/writes require the session credential and exact Host. POST additionally requires exact Origin; GET may omit Origin, but an Origin that is present must match. There is no CORS, directory server, arbitrary-path file endpoint or external asset. Packaged HTML/JS/CSS are the only page source; missing resources fail rather than falling back to cwd or the target. Captured text is rendered as text, and source line numbers follow LF/CRLF/CR physical boundaries.

## Repair candidates

Open **修复候选**, then enter absolute paths for the project directory, an already prepared neutral task JSON and a nonsecret model configuration JSON. The task declares the issue, source hashes, editable paths and protected public tests; use the [normal repair input contract](repair-entry.md#source-and-scoring-boundary), not answer or hidden-scoring files. The reading question does not automatically become repair authority. The browser submits proposal contract **v6** and offers `api_debugger`, `api_test_feedback` and `direct_api` under the same configured limits.

This calls the normal `repair_entry`/repair-loop flow. Default startup retains `verification_unavailable` for feedback strategies and `provider_disabled` for `direct_api`, with zero provider requests. The browser still submits only the same six fields: intent ID, project, task, nonsecret model configuration, strategy and proposal contract. It cannot supply a Key, enable transport/execution, select a spend cell or replace a backend. Authored transport and backend/replay fixtures check this connection without running a real model or target.

The panel shows running, saved-record verification and terminal states, request/token/local-cost summaries, and verified proposal/edit history when available. A saved record is not a verified fix. Retained candidates are distinguished from historical proposals; selecting an earlier candidate preserves the explicit **not rerun** verification status. Source is captured as data and candidates are saved in the owned workbench root; the original project is unchanged.

**修复记录** reopens registered results by verifying their saved output and summary, without rerunning the coordinator or rereading the original project/task/configuration. Failed or blocked runs remain visible; damaged records are withheld. A lost submission is resolved by its existing intent ID rather than posted again. Unknown outcomes or incomplete interrupted runs block new work, retain their records and are never automatically resumed. Repair has no cancellation button; exiting waits for its coordinator to finish.

### Controlled repair startup

Future real use requires explicit approval of the data, official API destination, model, budget and any execution operation. The implementation is not itself that approval. Official HTTP startup requires **all three** `--enable-remote-repair`, `--repair-spend-plan PATH` and `--repair-spend-cell ID`; a partial combination exits before creating the workbench or reading a Key. One fixed cell binds the exact task, strategy, model configuration and output contract. Each submission rechecks the unchanged plan; the existing durable ledger enforces ordered cells, unique claims, shared request/cost totals, model identity and per-request reservation. Copied output paths cannot replay a spent cell. Unknown outcomes halt instead of retrying. Declared prices are caller-frozen configuration, not freshly verified prices; local limits and receipts are not supplier-enforced caps, completion guarantees or invoices.

The normal entry reads the Key once through hidden foreground-terminal input before binding HTTP. It does not accept it from the browser, command arguments or environment, discover existing credentials, or save it in logs, records or persistent storage. Shutdown drops the session's references even when cleanup fails; Python strings and in-flight copies are not securely zeroized. In a remote session this terminal preparation happens at startup, before a task is submitted. A subsequent feedback run with no permitted verifier remains blocked before claiming a live cell or retrieving that credential for transport; the earlier startup prompt may already have occurred.

Execution separately requires `--enable-repair-verification` and an application-owned, side-effect-free factory returning an exact available `BackendVerifier`. Its backend identity and public-only receipt contract are retained; the browser cannot register a factory. The normal factory returns `None`, and there is no production backend registered: verification opt-in therefore fails before Key input or HTTP binding. A capability boolean, configuration flag or local hash is not execution authority or isolation attestation. A backend owner must separately establish authorized resources, isolation, bounds and cleanup; this path neither retries nor bypasses R10 or any stopped operation. See the [public verification contract](repair-public-verification.md).

A backend-reported public pass is `public_tests_reported_passed`, with origin `backend_reported_unattested`, `target_code_executed: null` and `repaired: false`. It is not a replay pass, independent execution proof or hidden-test score. The `simulation` field describes provider configuration and must not be used to infer backend authenticity. This implementation and its offline tests add no actual model or target execution evidence.

Validation must distinguish bounded pure branch fixtures, real loopback transport, actual native supervisor/pressure/RSS/closure, installed-resource checks and browser experience. Pure/mocked branch outcomes are not native acceptance. The previous installed-r3 macOS24/24 result does not itself validate this UI. Exact new native/browser results are recorded separately. The [second external real-project record](external-project-validation.md) retains failed attempts, passing checks for slots 1–6 and actual in-flight cancellation, and the restricted-RSS case's missing live OS identity. All eight fixed slots were attempted; overall evidence remains incomplete. Sustained/larger-load performance remains unverified; no model/VM/target-code acceptance is added.
